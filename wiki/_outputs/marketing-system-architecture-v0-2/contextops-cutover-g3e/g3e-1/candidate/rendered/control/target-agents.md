# Marketing ContextOps Agent

Marketing ContextOps is the active shared Context Intelligence capability of the federated Agentic Marketing System. Root `AGENTS.md` remains controlling for vault-wide source custody, durable knowledge, reusable-practice routing, permissions, and protected folders.

## Mission

Provide reusable, evidence-aware methods and contracts for company evidence intake, claim governance, market context, buying contexts, segmentation, audience understanding, framework fit, proof-led positioning, GTM context mapping, bounded handoffs, and independent ContextOps validation.

## Ownership boundary

- Marketing ContextOps owns reusable methods, stage contracts, framework-library conventions, and capability-specific validation.
- Root Second Brain owns default source custody, durable vault knowledge, and reusable-practice governance.
- The initiating source project owns every concrete market, Brand, positioning, GTM, campaign, content, run, approval, and episodic-learning artifact.
- ABM Operating System owns specialized account-based GTM execution methods.
- Content Operating System owns expression, channel, content-object, publication-state, and bounded editorial-learning contracts.
- Marketing Operating System remains a draft interoperability umbrella and gains no operating authority from this cutover.

## Required source-project routing

Before reading or writing concrete company artifacts:

1. Require one exact, existing repository-relative `source_project`.
2. Refuse a missing, ambiguous, nonexistent, or shared-system path.
3. Keep immutable sources in Root custody or an explicitly approved source-project custody path.
4. Write concrete derivatives only under the `source_project` according to its instructions.
5. Never create `raw/`, `research/`, `wiki/`, company assets, Brand Core, campaign assets, content stores, or run state under this shared system root.

The currently embedded Legacy company projects remain valid source projects until a separate reviewed admission or move changes their path.

## Stage discipline

- Consume an explicit upstream packet and perform one bounded decision job per stage.
- State scope, inputs, outputs, evidence status, downstream owner, and handoff questions.
- Label unsupported assumptions and stop before downstream decisions not explicitly requested.
- Use the smallest sufficient local framework set; route Root reusable-practice discovery through `wiki/reusable-practices-router.md`.
- Validate substantial cross-stage artifacts independently before downstream use.

## Learning governance

- Store successes, failures, corrections, and overrides as episodes in the initiating source project.
- Do not invoke or recreate the frozen standalone `recursive-learning-update` capability.
- Promote a pattern only after repeated evidence or a justified high-confidence exception, explicit human review, regression cases, and a rollback path.
- Method changes belong to the owning system and require their own reviewed change.

## Held dependency

`framework-builder` remains a Root-shared transitional dependency at the Legacy path. It may be read and used through its unchanged wrapper, but it may not be moved, edited, mirrored, or repointed without separate approval.

## Verification and maintenance

- Procedures belong in reviewed skills or workflows, not this always-loaded file.
- Keep framework and skill references repository-relative and resolvable.
- Run Root Wiki Integrity Fast and the reviewed Marketing ContextOps regression checks after structural changes.
- Append architecture or authority decisions to `decisions/log.md`; the log cannot grant its own authority.
- Any authority, routing, wrapper, contract, or component change requires exact preconditions, regression evidence, and a rollback path.
