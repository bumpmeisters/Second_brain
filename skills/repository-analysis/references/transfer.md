# Transfer and comparison lens

For each valuable mechanism record its problem, how it works, exact evidence, prerequisites and limits. Then make two judgments:

- Learning value: what becomes understandable; what future task could benefit?
- Adoption fit: A already covered; B bounded improvement candidate; C useful reference without current implementation need; D unsuitable for us.

Search existing wiki pages before choosing a target. A label C does not suppress valid knowledge. B requires a reason why the expected value exceeds adaptation and maintenance cost; when unknown, propose a bounded comparison rather than a benefit claim.

For development beyond the original, mark the proposal as our inference and specify what changes and how it could be tested. Do not attribute our extension to the repo. For cross-repo synthesis, compare the same job and evidence level and retain version-specific differences.

Keep proposed transfers in the dossier until authorized through the existing promotion process. Do not manufacture an implementation roadmap from every interesting pattern. Knowledge adoption, code reuse and runtime activation are different decisions; retain source attribution and check the particular license before copying code.
