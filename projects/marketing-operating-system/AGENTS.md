# Marketing Operating System Agent

This directory is an inactive control shell for a future federated Marketing Operating System. The root `AGENTS.md` remains fully controlling. These instructions narrow authority; they do not activate this system or replace any current owner.

## Current authority

- This shell has no operational or canonical authority.
- Do not route marketing work, knowledge, skills, workflows, assets, runs, or learning records here.
- Do not create a registry, contract, schema, tool, integration, runtime, evaluation, agent role, or additional folder here without a separately reviewed change set and explicit approval.
- Do not move, rename, copy, retire, or repoint any legacy, ABM, Content OS, source-project, root-skill, or protected-source component.
- The existing Marketing ContextOps project, ABM Operating System, Content Operating System, source projects, and root Second Brain retain their current boundaries.

## Target responsibility after activation

If later activated, this system may become the thin control and interoperability umbrella for:

- the marketing-system component registry;
- cross-system handoff and ownership contracts;
- shared Brand System and Campaign handoff contracts;
- Governed Pull, runtime, learning, and cross-system evaluation contracts;
- architecture validation and compatibility decisions.

This target role is descriptive, not executable authority.

## Ownership boundaries

- Root Second Brain owns source custody, durable wiki knowledge, vault-wide governance, and skill discovery.
- Marketing ContextOps owns reusable Context Intelligence methods and stage contracts after its own activation.
- ABM Operating System owns its specialized account-based GTM capability.
- Content Operating System owns shared content transformation and publication contracts.
- Company and thematic source projects own concrete market, Brand Core, positioning, GTM, campaign, content, approval, run, and episodic-learning artifacts.
- This umbrella must not own or duplicate those concrete artifacts.

## Review and maintenance

- Keep this file concise and limited to durable mission, authority, boundaries, and activation rules.
- Put procedures in reviewed skills or workflows only after a real recurring need exists.
- Record architecture or authority decisions in `decisions/log.md`; the log cannot grant its own authority.
- Before any activation proposal, prove one owner per component, no protected-source change, no operational reference break, and a tested rollback path.
