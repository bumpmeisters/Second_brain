# Second Brain Framework Fit

## Overview

Use this skill to choose a small, relevant framework stack from the project-local `frameworks/` library. Use Rolf's Second Brain as a discovery and gap-filling source, not as the normal execution dependency.

## Operating Principles

- Start with company/product evidence, not favorite frameworks.
- Treat frameworks as methods, not as evidence for company facts.
- Select a small stack, usually 3-7 frameworks.
- Explain why each framework fits, what it enables, and what should be deferred.
- Record fit decisions so later runs can learn which frameworks transferred well.

## Workflow

1. Read the current company context.
   - Start with project index, source register, log, context dossier, claim matrix, and user goal.

2. Search the local framework library.
   - Read `../../frameworks/index.md`.
   - Read the relevant domain index and compare candidate framework documents.
   - Load only the selected framework documents.
   - If the local library has a genuine gap, read `wiki/second-brain-source-map.md` and search the parent wiki as a discovery source.
   - Do not apply a newly discovered framework repeatedly until it has been curated into `frameworks/`.

3. Select frameworks.
   - Read `references/framework-selection-rules.md`.
   - Choose 3-7 frameworks with explicit reasons.
   - Defer frameworks that require missing inputs.

4. Map frameworks to outputs.
   - Read `references/framework-output-map.md`.
   - Read `workflows/contextops-handoff-contract.md` from the project root when this skill is used inside the marketing-agent vault.
   - Define what each framework enables next: claim matrix, message house, persona hypotheses, journey map, campaign architecture, sales enablement, GTM plan, brief, or measurement plan.

5. Create the framework fit note.
   - Include recommended stack, deferred frameworks, open inputs, and next artifact.

6. Prepare for learning.
   - Read `references/framework-retrospective-template.md` when reviewing a completed run.
   - Record which frameworks were useful, weak, premature, or missing.

## Quality Gate

Before finishing, verify:

- The selected frameworks respond to the actual company/product problem.
- Local canonical framework documents were preferred when available.
- The stack is small enough to execute.
- Deferred frameworks have a clear reason.
- Each framework has a next artifact.
- Framework claims are not treated as company facts.
