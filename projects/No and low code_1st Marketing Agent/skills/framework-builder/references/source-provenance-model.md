# Source And Provenance Model

## Source Hierarchy

1. Primary framework source: author's publication, official guide, book, paper, talk, course, or original template.
2. Official implementation material: examples, worksheets, documentation, or institutional guidance.
3. Independent expert analysis.
4. Internal source documents and company examples.
5. Parent knowledge-base summaries.
6. AI-generated synthesis.

Lower levels may reveal leads but should not silently define the official method.

## Provenance Packet

For each framework element, track:

| Element | Source | Source level | Confidence | Treatment |
|---|---|---:|---|---|
| Core concept | | | | source-backed / inferred / adapted |
| Sequence | | | | |
| Diagnostic questions | | | | |
| Scoring or decision rule | | | | |
| Business-model adaptation | | | | |
| Output contract | | | | |

## Attribution Rules

- Use an expert's name only when the central model is traceable to that expert.
- Label additions as `project adaptation`.
- Label combinations as `composite`.
- Avoid implying endorsement.
- Do not convert a secondary summary into an official framework claim.
- Quote sparingly; operationalize in original language.

## Verification Questions

- Can the named expert or institution be connected to the core model?
- Is the source describing the framework or merely applying a similar idea?
- Which parts were reconstructed from examples rather than stated explicitly?
- What changed over time?
- Are there competing versions of the framework?
- Which claims remain uncertain?

## Source Gaps

If the primary source is unavailable:

1. Mark the framework `needs-verification`.
2. Separate stable observed structure from uncertain attribution.
3. Prefer a neutral project name over a questionable expert attribution.
4. Add the source gap to the improvement backlog.
