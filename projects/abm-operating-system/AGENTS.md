## Operating principles

### 1. Make every artifact earn its maintenance cost

Create a register, directory, copy, or control only when it owns a distinct recurring decision that an existing parent-vault artifact cannot handle without ambiguity. Reference existing custody and navigation instead of duplicating them. At review gates, merge or retire unused structures.

### 2. Keep source custody in the parent vault

The parent vault's `raw/`, `raw/assets/`, `research/`, `research/assets/`, `wiki/_extractions/`, and `wiki/sources.md` remain authoritative for source custody and discovery.

- Never modify files in `raw/`, `raw/assets/`, or `research/assets/`.
- Do not create a second raw library or project source register.
- Cite stable repository-relative paths.
- Before reading a binary source at content level, follow the parent vault's sidecar-readiness rule.
- Treat AI-generated research as leads until important claims are verified against primary evidence.

### 3. Separate evidence, cases, patterns, and canonical principles

Knowledge moves through governed layers:

`source evidence → Blueprint Challenge Record → candidate pattern → reviewed principle → canonical framework decision`

Permitted promotion outcomes are `confirm`, `extend`, `contradict`, `contextualize`, and `reject`. A single case or vendor claim cannot silently alter the Enterprise Growth System.

### 4. Maintain one canonical Enterprise Growth System

The ABM Operating System owns the only editable Enterprise Growth System. The Marketing Agent consumes it through a direct cross-project reference and must not maintain an editable or generated local copy.

### 5. Separate framework promotion from publication

Framework promotion asks whether private canonical knowledge should change. Publication approval asks whether an exact reviewed artifact may leave the private system. Neither approval implies the other.

Any future publication record must bind approval to:

- exact artifact path and version;
- content fingerprint;
- approver and approval time;
- approved channel;
- source-rights decision.

Any substantive edit invalidates the approval.

## Confidentiality and storage

Confidentiality and publication status are separate fields.

| Class | Examples | Approved project handling | External AI processing | Publication default |
|---|---|---|---|---|

| `personal-data` | Identifiable stakeholder, contact, behavioral, or employment information | Do not place in ordinary Git-tracked project files; minimize and use an approved controlled location | Prohibited unless explicitly approved and necessary | `private` |

Current seed material is user-confirmed as non-sensitive. Named or recognizable real-company cases nevertheless remain publication-gated. If future material appears client-derived, personally identifiable, or otherwise sensitive and the user has not classified it, stop and ask before ingesting its content.

## Efficient read-write protocol

Apply these rules without weakening source, approval, or validation controls:

1. **Verify paths before use.** Confirm that every intended path exists before reading, editing, hashing, or citing it. If an expected target is missing, search this project first and the parent vault second; stop when multiple candidates remain ambiguous. For similarly named or duplicate sources, treat the verified repository-relative path plus content fingerprint as the working identity. Classify targets as source, canonical, derivative, control, or unrelated and define the exact read/create/update set.
2. **Read progressively.** Search inside this project first. Read frontmatter, headings, and relevant sections before loading full project documents; read a complete source or artifact when its full reasoning is required. Do not run broad vault searches unless the expected local artifact is missing.
3. **Separate writing passes.** Complete content artifacts before governance and navigation updates. Patch one file at a time. If a patch has not completed after roughly 30 seconds, stop it, inspect the actual target state, and continue only from what remains. Use the parent vault's transactional fallback for an existing file only after the normal patch mechanism fails or hangs.
4. **Compare the task delta.** Before writing, capture the relevant working-set status, intended target fingerprints, and protected-source state. After writing, compare the same scope and report only what the task introduced; preserve and exclude pre-existing dirty or untracked work from the task result.
5. **Validate in two levels.** After each file, check the intended change, frontmatter/heading structure, formatting, affected links, and stale state locally. Run the full protected-hash, canonical-count, cross-link, temporary-file, diff, staging, and scope audit once after the complete write set rather than repeating it between small edits.
