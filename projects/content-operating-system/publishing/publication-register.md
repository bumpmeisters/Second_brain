# Publication Register

**Summary**: Cross-project record of externally usable content variants, their governing Creative Directions and briefs, actual approval state, and publication evidence. It references source-owned artifacts and never replaces source-project approval records.

## Status vocabulary

`idea` -> `briefed` -> `draft` -> `in-review` -> `approved-not-published` -> `published` -> `retired`

Approval and publication are separate. A substantive edit to an approved artifact creates a new version and normally returns it to `in-review`.

## Required fields for new entries

- stable `content_id`;
- exact `direction_id`;
- unique `variant_id` or explicit fingerprint-governed bundle ID;
- primary source project;
- exact source-owned bundle brief;
- exact artifact path;
- `embedded` or `registered-legacy` metadata mode;
- channel and language;
- actual status;
- date the status was last checked;
- approval record when applicable;
- publication date and public URL or other evidence when published;
- notes for fingerprints, rights, bundles, experiments, or limitations.

## Register rules

- Register publishable variants, not every working note.
- Every row must resolve to an existing direction, source brief, and artifact.
- New assets embed lineage in frontmatter. `registered-legacy` is reserved for migrated assets whose bytes must remain unchanged.
- Do not mark an item `approved-not-published` without an explicit approval record.
- Do not mark an item `published` without publication evidence.
- Preserve the controlling source project's stricter gate.
- Record a new row for a materially different channel, audience, language, tone, format, test, or version.
- A bundle may share one artifact and approval fingerprint, but every separately publishable unit still receives its own row.
- Retain retired rows for provenance.
