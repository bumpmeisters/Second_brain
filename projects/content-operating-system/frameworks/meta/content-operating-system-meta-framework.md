# Content Operating System Meta-Framework

**Summary**: A provisional router that separates framework intelligence from the canonical context-to-content transformation chain, selects the smallest suitable method, and preserves ownership, evidence, publication, and learning boundaries.

## Framework Job

Decide which Content Operating System stage owns a content problem, which upstream authority or content method is required, what inspectable output must be produced, and where the result must hand off next.

The framework serves Rolf and bounded agents working across content strategy, creative direction, execution, publication, and learning. It must not copy or silently reopen source-project evidence, audience decisions, positioning, claims, campaign roles, approvals, or publication authority.

## Classification And Fidelity

This is an **original project framework**. It synthesizes the existing Content Operating System strategy, object model, lifecycle runbook, two canonical decision frameworks, and relevant vault practices. It is not an official method from any named expert.

Source-backed and previously approved project elements:

- source-project ownership and referenced ContextOps intake;
- the Strategic Creative Direction and Content Brief split;
- the direction → brief → triggered execution calibration → asset → publication → learning chain;
- separate approval and publication states;
- bounded performance learning and explicit evolution decisions.

Project-created elements introduced here:

- the dual-plane distinction between Framework Intelligence and the transformation chain;
- the artifact-status and method-routing vocabulary;
- the architecture tournament and meta-level question engine.

These additions remain hypotheses until the first two real end-to-end runs are reviewed.

## Use When

- The request spans several content stages or frameworks.
- It is unclear whether the problem belongs upstream, to Creative Direction, to Content Execution, to publishing, or to learning.
- Several frameworks appear to solve the same decision.
- A content-framework family needs classification before reconstruction or promotion.
- A new system capability is being considered.

## Do Not Use When

- One bounded task already has a ready Context Packet and an approved route.
- The exact approved `direction_id` and appropriate Content Execution path are known.
- The user is asking only for a content draft under an existing brief.
- The actual decision belongs to a source project, Marketing ContextOps, claim governance, legal review, or publication approval.

## Minimum Required Inputs

- the requested decision and intended output;
- source project and upstream authority;
- available context and evidence state;
- current content object and publication state, when one exists;
- candidate frameworks or practices, when selection is disputed;
- ownership, rights, review, capacity, and timing constraints.

Missing material context produces a routing gap, not invented downstream strategy.

## Core Model

### Plane A: Framework Intelligence

Framework Intelligence discovers, classifies, compares, and routes methods without copying them or treating source abundance as authority.

| Class | Meaning | System treatment |
|---|---|---|
| Project framework | Content OS owns the decision method. | Store under `frameworks/`; evaluate before activation. |
| Upstream authority | Another project or wiki authority owns the decision. | Reference through the Context Packet. |
| Registered specialist practice | A bounded vault method has explicit triggers and guardrails. | Route to it when its `use_when` matches and `avoid_when` does not. |
| Candidate synthesis | Useful material exists, but no evaluated reasoning method is canonical. | Build a provenance packet before framework work. |
| Reference-only | Source summary, AI research cluster, extraction, or version trail. | Use for discovery and evidence, not execution authority. |

The detailed classification is maintained in [the artifact inventory](../_meta/artifact-inventory-2026-07-28.md).

### Plane B: Canonical transformation chain

```text
canonical evidence and knowledge
  -> referenced Content Context Packet
  -> Strategic Creative Direction
  -> Content Brief and Content Execution
  -> Execution Calibration when expression uncertainty is material
  -> content asset and truthful publication state
  -> Performance Record and bounded learning decision
```

| Stage | Decision job | Canonical owner or method | Stop condition |
|---|---|---|---|
| Context intake | Is upstream context sufficient and safe to use? | Source project plus `contextops-intake-contract.md` | Stop on `blocked`. |
| Strategic Creative Direction | What should be said and why? | `strategic-creative-direction.md` | Stop before channel-specific execution. |
| Content Execution | How should one coherent variant bundle express it, and is calibration required before a full draft? | `content-execution.md` plus its support contracts | Stop before publication authority or performance interpretation. |
| Asset and publication state | What exact artifact exists, and what is its truthful state? | Source project plus publishing profiles and register | Publication requires direct instruction. |
| Performance and learning | What was observed, what might it mean, and what changes are proposed? | Performance Record plus evolution owner | Signals do not automatically change claims, frameworks, or strategy. |

### Optional portfolio and architecture branch

Strategic pillars, editorial territories, buyer questions, topic clusters, hubs, content models, journeys, formats, and asset portfolios are visible in the source inventory but do not yet form a canonical project framework. When a real assignment depends on those decisions, route upstream or create a bounded source packet; do not silently add a portfolio object, content backlog, calendar, or universal architecture.

### Three operating rails

1. **Evidence and governance** — provenance, claims, uncertainty, freshness, rights, confidentiality, review, approval, and retirement.
2. **Ownership and process** — source custody, decision rights, handoffs, capacity, status, cadence, and escalation.
3. **Identity, data, AI, and tools** — stable object IDs, lineage, voice and channel profiles, retrieval context, validation, automation boundaries, and evaluation.

The rails apply throughout the transformation chain; they are not end-of-process checks.

### Architecture tournament

| Candidate | Description | Fidelity | Inference leverage | Context fit | Evidence discipline | Composability | Efficiency | Evolvability | Weighted result |
|---|---|---:|---:|---:|---:|---:|---:|---:|---:|
| A. Extended lifecycle | Add strategy, portfolio, creation, distribution, and measurement to one long chain. | 3 | 4 | 4 | 3 | 3 | 4 | 3 | 3.50 |
| B. Capability stack | Organize strategy, editorial, production, channels, data, and governance as peer capabilities. | 3 | 3 | 4 | 4 | 4 | 4 | 4 | 3.60 |
| C. Dual-plane router | Keep Framework Intelligence separate from the approved transformation chain and apply cross-cutting rails. | 5 | 5 | 5 | 5 | 5 | 4 | 5 | 4.90 |

Candidate C is selected. It preserves the approved project boundary and transformation chain while making the wide framework library routable. Candidate A remains a useful simplified communication view. Candidate B remains useful for future capability assessment.

## Question Engine

### Minimum Viable Questions

1. What exact decision and inspectable output are requested?
2. Which source project owns the underlying evidence and thesis?
3. Which stage of the transformation chain owns the current decision?
4. Is the required upstream context `ready`, `ready-with-hypotheses`, or `blocked`?
5. Does a canonical project framework already cover the job?
6. Does a registered specialist practice match without violating its boundary?
7. Is the proposed method a reconstructed framework, a candidate synthesis, or only a source/version trail?
8. What meaning, evidence, rights, state, and ownership must the handoff preserve?
9. Which direct user decision or approval is still required?
10. What observation would cause the method or route to be reconsidered?

### Deepening Questions

- Which answer would materially change the stage or method selection?
- Is the team trying to solve an upstream strategy problem during execution?
- Are two methods actually competing, or do they own different decisions?
- Is a pillar an editorial territory, a campaign theme, a topic cluster, or a format label?
- Is a story method choosing the argument or only its expression?
- Does the proposed output create reusable intellectual content or one channel-bound variant?
- What would a skeptical reviewer say is unsupported, generic, or outside the approved boundary?

### Counter-Questions

- What if no new asset or framework is needed?
- What if an existing asset should be refreshed, redistributed, combined, or retired?
- What if high engagement reflects attention rather than usefulness or strategic validity?
- What if AI-generated polish is hiding a weak direction or unsupported claim?
- What if the proposed system addition duplicates source-project custody or an existing register?

### Optional Modules

- Artifact inventory and overlap analysis.
- Source and provenance packet for one candidate family.
- Architecture tournament for a proposed framework.
- Context readiness and leakage review.
- Canonical transformation-chain audit.
- Publication-state and lineage audit.
- Framework evolution review after application evidence.

## Branching And Stop Rules

- Missing business, audience, positioning, claim, proof, or campaign-role context returns upstream.
- An unapproved content core routes to Strategic Creative Direction.
- An approved `direction_id` with an expression problem routes to Content Execution; personal-authority, weak-baseline, early-pilot, or prior-rejection cases trigger calibration.
- A change to audience, thesis, proof, angle, desired response, or Personal Take returns to Strategic Creative Direction.
- Drafting or review authority never implies publication authority.
- Performance observations never automatically validate claims, frameworks, or causality.
- A source-summary, model-labeled file, duplicate version, or extraction cannot become canonical without reconstruction and evaluation.
- A proposed new project framework requires an explicit decision and evolution record.
- Stop loading optional modules when further investigation would not change the route or output.

## Evidence Standard

Separate observed fact, source claim, internal judgment, model inference, synthetic hypothesis, and unresolved question. Preserve repository-relative provenance and source-project custody.

Framework evidence and business evidence are different layers. An evaluated method does not make its content claims true, and content performance does not prove the method or upstream thesis.

AI-generated research and model-labeled working files may support discovery but remain non-canonical until reviewed and, where material, checked against primary or official sources.

## Business-Model Adaptations

- **Complex B2B**: preserve buying roles, account context, decision criteria, long cycles, and proof requirements.
- **ABM or pursuit work**: preserve one primary source project, account-specific relevance, approved promise, and exact evidence boundaries.
- **Thought leadership**: treat the thesis and evidence pack as the direction core; formats remain downstream variants.
- **Small pilot**: use one source project, one direction, one coherent brief, one bounded asset set, and one review record.
- **Transactional work**: simplify role and lifecycle depth while retaining context readiness, evidence, ownership, publication, and learning controls.

Adaptations change the required inputs and depth, not the ownership boundary.

## Output Contract

A routed Content OS decision contains:

- requested decision and output;
- source project and upstream authority;
- selected transformation stage;
- context readiness and evidence boundary;
- selected canonical framework, registered practice, or candidate-status decision;
- required content object, owner, and truthful state;
- preserved invariants, rights, and open questions;
- next handoff, approval requirement, and review trigger.

## Failure Modes

- Building a second source of truth for context or assets.
- Treating every useful content method as a project framework.
- Calling a source collection a framework.
- Treating pillars, storytelling, hooks, and writing rules as the same decision.
- Reopening strategy during drafting.
- Treating AI fluency, anti-slop checks, or content distinctiveness as proof of voice and editorial craft.
- Choosing channels or hooks before the content core is approved.
- Treating publication as completion or drafting as publication authority.
- Treating performance as causal proof.
- Expanding the system before a repeated decision or failure is observed.

## ContextOps Handoff

| Route | Preserve | Handoff |
|---|---|---|
| Upstream gap | Missing decision, evidence, owner, and impact | Source project or Marketing ContextOps |
| Context ready | Exact references, claims, rights, and hypotheses | Strategic Creative Direction |
| Direction approved | `direction_id`, invariants, proof, exclusions, desired response, and calibration trigger | Content Execution |
| Asset reviewed | IDs, exact artifact, state, approval, and channel boundary | Publishing |
| Performance observed | Exact variant, observation, alternatives, limits, and proposal | Evolution owner |

## Evaluation Notes

First application: classification of 32 pre-existing curated wiki artifacts, two existing project frameworks, and 385 potentially content-relevant sidecar extractions.

| Dimension | Score | Note |
|---|---:|---|
| Fidelity and attribution | 5 | Existing project ownership and chain are preserved. |
| Inference leverage | 5 | Framework-library classification is separated from content transformation. |
| Evidence discipline | 4 | Source summaries and AI variants remain non-canonical. |
| Context fit | 5 | Fits the existing project structure and B2B context. |
| Composability | 5 | External authorities and specialist practices are routed, not copied. |
| Efficiency | 4 | Minimum questions and optional modules limit context load. |
| Reliability | 2 | Only an inventory case exists; no real end-to-end run has tested this router. |
| Evolvability | 5 | Inventory, decision record, backlog, and promotion boundary are explicit. |

The weak-evidence test leaves hooks, generic storytelling, writing rules, and content-architecture families at candidate status. The wrong-fit test keeps audience, brand, claims, and campaign-role decisions upstream. The framework stays `draft`.

## Evolution Triggers

Review after:

- each of the first two real end-to-end Content OS runs;
- one documented framework-selection ambiguity;
- one repeated need for a portfolio or content-architecture decision;
- one conflict between a project framework and a routed specialist practice;
- one proposed new canonical project framework.

Known gaps and the prioritized candidate families are recorded in [the artifact inventory](../_meta/artifact-inventory-2026-07-28.md) and `evolution-backlog.md`.
