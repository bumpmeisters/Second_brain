## Creator description

You will start with a simple model call and leave with a fully functional customer-service agent. Along the way, you will add the reasoning loop, tools, state, context, guardrails, an agent SDK, and MCP, then learn how to adapt the architecture to your own enterprise use cases.

Most advice about agent harnesses comes from coding agents. That becomes a problem when you are building a support agent that should resolve a request in one reply, a workflow with one reasoning step, or an enterprise agent with a small number of tightly controlled tools.

In this Lightning Lesson, I build a working computer-use agent with four tools and roughly 147 lines of Python, then use it to organize a desktop through a reasoning loop. I also show how the same four-tool pattern runs part of my real YouTube publishing workflow: finding clips, cutting them with FFmpeg, adding word-highlighted captions and the Vanishing Gradients logo, verifying the results, and uploading drafts through the YouTube API.

We then examine:

• Why a workflow containing LLM calls is not automatically an agent
• How Pi keeps the core agent small while OpenClaw grows a product around it
• Why coding, deep-research, support, and conversational agents need different harnesses
• How action complexity and context complexity help you decide what to build
• Why every harness feature is a bet on something the model cannot reliably do
• Why runtime agent harnesses and eval harnesses solve distinct problems
• How production failures should determine which machinery you add next
